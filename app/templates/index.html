Where the data comes from

Two sources of GitHub Actions runs, joined end to end in time.

GADFPD

GitHub Actions CI/CD Failure Prediction Dataset by Faruna et al. (2026), Mendeley Data, DOI 10.17632/mggwn7rj9f.1. Licence CC BY 4.0. Covers runs from 8 August 2016 to 18 April 2026.

Own collection

23,818 workflow runs from 14 public repositories, 19 April to 20 November 2026, collected with the GitHub REST API. Repository and actor names are hashed and no commit message text is stored.

Only runs with a clear success or failure outcome and a first attempt are kept. Runs are sorted by time and split 70% train, 15% validation and 15% test, so the test set is always the most recent data.

How it was built

Six algorithms were tuned: Logistic Regression, Decision Tree, KNN, Linear SVM, Random Forest and Histogram Gradient Boosting. Each used randomized search with 5-fold time-series cross-validation, and the winner was picked by validation macro-F1. That was , trained with class weights.

It uses features: change size, merge flag, hour, weekday, branch, trigger event, and run history (previous outcome, failure rate over the last 10 runs, number of earlier runs) for both the repository and the workflow.

Limitations

  • Failures are fairly rare. At the chosen threshold the model finds about of them, so it misses some failures and raises some false alarms.
  • Most of the signal comes from run history. A brand new repository or workflow is judged mainly on change size and trigger.
  • The failure rate differs between the two data sources, and repositories change over time, so the model should be retrained periodically.
  • The score ranks runs. It is not a literal probability of failure, because of the class weights.
